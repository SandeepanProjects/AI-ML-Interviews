# Function Calling / Tool Calling in LLMs — From Fundamentals to Production

Tool calling is a mechanism that allows an LLM to request that your application execute a specific function or external tool. The application executes the tool, sends the result back to the model, and the model uses that result to produce its next response.

This is one of the most important concepts in agentic AI systems because an LLM by itself generally cannot query your private database, call your internal APIs, execute your business logic, or retrieve live information unless the surrounding application provides those capabilities.

For example, imagine you're building your financial compliance AI platform. A user asks:

> Check whether this investment claim is supported by our approved compliance policies.

The LLM needs to retrieve the relevant policy documents before answering. Instead of guessing, it can request a tool call such as `search_compliance_policies`.

Your application executes that function against the policy database and returns the retrieved evidence to the LLM.

## 1. How tool calling works

1\. User asks a question

"Find the policy governing guaranteed investment returns."

2\. LLM selects a tool

Requests `search_compliance_policies` with structured arguments.

3\. Application executes the function

Checks authorization and queries the policy repository.

4\. Tool returns its result

Returns policy excerpts, identifiers, and versions.

5\. LLM generates its answer

Uses the returned evidence to explain the result.

The critical idea is that the LLM requests the tool call, but your application executes it. The model does not automatically gain access to your Python runtime, database, or network just because a function is described to it.

## 2. What is the difference between a normal LLM response and a tool call?

Suppose the user asks:

> What is the current balance in account 123?

A normal LLM response might be:

> Your balance is ₹50,000.

That answer is dangerous if the model has no reliable access to the account data. It might simply invent a number.

A tool-enabled application can instead provide a function:

```
def get_account_balance(account_id: str) -> dict:    # Real implementation would query an authorized account service.    ...
```

The model may request:

```
{
  "name": "get_account_balance",
  "arguments": {
    "account_id": "123"
  }
}
```

Your application then:

1. Validates the arguments.
2. Checks that the authenticated user is authorized to access the account.
3. Calls the account service.
4. Returns the result to the model.
5. Lets the model explain the result.

The JSON shown here illustrates the concept; actual tool-call payloads depend on the model provider's API.

Tool calling is not the same as executing arbitrary code generated by the model. In a safe design, the application exposes a limited set of known, explicitly implemented functions.

## 3. Implement tool calling using Python — without an LLM first

Before connecting a language model, understand the function-execution mechanism itself.

Let's build a small tool registry. A registry maps approved tool names to Python functions.

```
from typing import Any, Callabledef get_weather(city: str) -> dict:    # Demo implementation: no live weather data.    return {        "city": city,        "temperature_celsius": 28,        "condition": "Cloudy",    }def calculate_compound_interest(    principal: float,    annual_rate: float,    years: int,) -> dict:    amount = principal * (1 + annual_rate / 100) ** years    return {        "principal": principal,        "final_amount": round(amount, 2),        "interest_earned": round(amount - principal, 2),    }TOOLS: dict[str, Callable[..., Any]] = {    "get_weather": get_weather,    "calculate_compound_interest": calculate_compound_interest,}def execute_tool(    tool_name: str,    arguments: dict,
```

Expected result:

```
{
  "principal": 100000,
  "final_amount": 146932.81,
  "interest_earned": 46932.81
}
```

This example demonstrates the execution layer, but it is not yet a complete production tool-calling system.

### Understand each component

- `TOOLS` is the allowlist of functions the application is permitted to execute.
- `tool_name` identifies which function should run.
- `arguments` contains the function inputs.
- `execute_tool()` dispatches the request to the corresponding function.
- The function result is returned to the caller.

In production, don't blindly execute arbitrary arguments using `tool(**arguments)`. Validate them against a schema, enforce timeouts and resource limits, handle errors, and apply authorization checks inside the relevant service.

Also, the weather function returns hardcoded demonstration data. It does not fetch live weather.

### What happens when you run this code?

1. Tool registration: The application tells the model what `calculate_compound_interest` does and what arguments it requires.
2. Model decision: The model can request that function because the user's question requires a calculation.
3. Function execution: Your code reads the tool-call arguments, looks up the function in the allowlist, and runs the Python function.
4. Tool result: Your code serializes the returned dictionary into JSON and associates it with the tool's `call_id`.
5. Final answer: The model receives the tool result and explains the calculated amount in natural language.

For this example, the expected calculation is a final amount of ₹146,932.81 and interest earned of ₹46,932.81.

The model does not perform the actual Python function execution. It emits a request; your code executes the function and returns the result.

Important production improvement: the sample raises an exception for invalid arguments and unknown tools. A production implementation should convert expected tool errors into controlled tool-result messages, apply retry limits, and preserve enough information for the model or orchestrator to recover safely.

## 5. How does the model know which tool to call?

The model uses the tool's name, description, parameter schema, and the conversation context to decide whether a tool is useful.

For example, suppose the application exposes these tools:

| Tool               | Purpose                            |
| ------------------ | ---------------------------------- |
| `search_policies`  | Retrieve relevant policy documents |
| `calculate_return` | Calculate an investment return     |
| `get_portfolio`    | Retrieve an authorized portfolio   |
| `create_review`    | Create a compliance review record  |

If the user asks, "Calculate the annualized return," the model may select `calculate_return`.

If the user asks, "Which policy covers this claim?" it may select `search_policies`.

The model's choice is not guaranteed to be correct. A production application must check that the requested tool is allowed and that the supplied arguments are valid.

There are also different tool-selection modes, depending on the provider:

- Automatic: the model chooses whether to call a tool.
- Required: the model must request a tool call, if the API supports that mode.
- Forced specific function: the API requires a particular function, where supported.
- No tools: the model responds without using tools.

Forcing a function call does not mean the function's result will be correct. It only influences the tool-selection behavior.

## 6. Tool calling versus structured output

These concepts are related, but they serve different purposes.

Structured output

The model returns a typed data object that follows a schema.

Example: a compliance result with `risk_level`, `findings`, and `requires_human_review`.

Tool calling

The model requests an action for your application to execute.

Example: `search_policies(query="guaranteed annual returns")`.

You can use both in the same workflow. For instance, an LLM can call a retrieval tool and then return the final review as structured JSON.

A tool call is itself often represented using structured arguments, but the purpose is different: the arguments specify an action, whereas the final structured response represents data.

## 7. How to implement tool calling safely in a financial AI platform

Consider a tool that retrieves compliance policies.

A simplified tool definition might be:

```
def search_compliance_policies(    query: str,    tenant_id: str,) -> dict:    ...
```

The model may request:

```
{
  "query": "guaranteed investment returns",
  "tenant_id": "tenant-123"
}
```

But this design has a security problem if `tenant_id` comes directly from the model. The model must not be allowed to choose which tenant's private documents it can access.

Instead, derive the tenant and user identity from the authenticated request:

```
async def search_policies_tool(    query: str,    authenticated_context,):    tenant_id = authenticated_context.tenant_id    return await policy_service.search(        tenant_id=tenant_id,        query=query,    )
```

The authenticated context here is provided by your application—not generated by the model.

For production, apply these principles:

- Allowlist: only execute explicitly registered tools.
- Validate: check arguments using Pydantic or JSON Schema.
- Authorize: check user permissions inside the relevant service.
- Isolate tenants: derive tenant identity from trusted authentication context.
- Limit resources: set timeouts, query limits, and maximum result sizes.
- Audit: record the requested tool, caller, arguments after appropriate redaction, result status, and correlation ID.
- Handle untrusted content: treat retrieved documents and tool results as data, not as new instructions to override system policy.
- Require approval: gate consequential actions such as executing transactions, publishing compliance decisions, or modifying important records.

A model's request to call a function is not authorization to perform that function.

## 8. Production pattern: multiple tool calls and controlled execution

In an enterprise agent, the model may need more than one tool.

For example:

1. Retrieve the customer's portfolio.
2. Retrieve the relevant compliance policy.
3. Calculate the portfolio's return.
4. Produce a structured review using the returned evidence.

Your orchestration layer should support a bounded loop rather than assuming that one model call and one tool call are always sufficient.

A production orchestrator should also handle:

- Multiple tool calls in one model response.
- Tool exceptions and timeouts.
- Invalid arguments and unknown tools.
- Maximum tool calls and maximum workflow steps.
- Duplicate execution and idempotency for state-changing operations.
- Model refusals and incomplete responses.
- Logging, tracing, latency, and cost.

Read-only tools can often be retried safely. State-changing tools need additional safeguards: a retry must not accidentally create the same review twice or submit a transaction twice.

## 9. How tool calling fits into LangGraph and agentic AI

In LangGraph, tool calling is often implemented using a model node and a tool-execution node.

Agent node

LLM chooses a tool or prepares a final response.

Conditional router

Routes to tools when a valid tool call exists; otherwise routes to completion.

Tool node

Executes approved functions and adds results to workflow state.

Return to the agent with the tool result until the task is complete or a limit is reached.

A typical LangGraph implementation uses:

- `ChatOpenAI` or another compatible chat model.
- `bind_tools()` to expose tool definitions.
- `ToolNode` to execute supported tool calls.
- `tools_condition` to route between the agent and tools.
- Typed state to preserve messages and workflow information.
- Checkpointing and interrupts when durable execution or human approval is required.

These components handle orchestration; they do not remove the need for tool-level authorization and validation.

Also, not every tool needs to be an LLM tool. Deterministic calculations, database operations, and policy validation should usually be ordinary Python services. Expose only the operations the model genuinely needs to choose among.

## 10. What you should remember for senior AI engineering interviews

If an interviewer asks, "How do you implement tool calling in production?", a strong answer is:

> I expose a controlled set of tools with descriptions and typed input schemas. The LLM selects a tool and generates structured arguments, but the application validates the request, enforces authorization, executes the actual function, and returns the result to the model. I use a bounded orchestration loop with timeouts, retries, idempotency for state-changing operations, observability, and explicit error handling. For multi-agent workflows, I use typed state and conditional routing, and I require human approval for high-impact operations.

The core difference is simple:

- An LLM without tools can generate an answer from its context and learned patterns.
- An LLM with tools can request that the surrounding application perform real operations and use the returned results.
- An enterprise agent adds authorization, validation, orchestration, observability, and failure recovery around those operations.

That's the foundation of reliable tool use in RAG systems, multi-agent applications, and production AI platforms.
